# Test ideas from the earlier CLI bridge

Date checked: 2026-10-18 (Asia/Taipei). The newest source is of 2026-10-15.

Provenance: This note collects the test ideas and the test facts of the notes and the test files of an earlier project, the earlier CLI bridge. That project was a bridge that used the Antigravity CLI (`agy`) as its engine, and late in its life it planned a change to the official runtime. The maintainer wrote the sources between 2026-10-04 and 2026-10-15 (Asia/Taipei). The source notes are, by their old file names: `docs/plan/mvp-spec.md` (sections "Endpoints", "Parameters", "Conversations", "Gate and queue", "Tools", "Signals and stops", "Acceptance test", "Security", "Log", "Testing Decisions"), `docs/plan/mvp-tickets.md` (tickets T01 to T23), `docs/plan/acp-engine-plan.md` (2026-10-15, sections 3, 5, 6, 10, and 11), the first live acceptance note (2026-10-06) (live check of 2026-10-06), and the second live acceptance note (2026-10-06) (live checks of 2026-10-06 and 2026-10-08). The other sources are the files in `test/` of that project, last changed on 2026-10-13. The note moved to acp2api on 2026-10-18, because that project will be deleted. On 2026-10-18, each idea was compared with the decisions of the map issue #1, its closed sub-issues, and ADR-0001 to ADR-0006.

Words of the earlier project:

- **the earlier bridge**: the short form of "the earlier CLI bridge", the project that this note comes from.
- **the maintainer**: the old word was "operator".
- **harness**: an API client, for example Claude Code, Codex, or OpenCode.
- **engine**: the Antigravity CLI `agy`. In `acp-engine-plan.md`, the official runtime, which that plan calls "the ACP server".
- **engine process, server process**: a process of the CLI, or, in the ACP plan, the runtime process.
- **Cascade**: a conversation of the CLI engine. In the ACP plan, one ACP session.
- **turn**: one input line of the CLI and its result (this note says "CLI turn"). In the ACP plan, one prompt turn.
- **slot, gate**: the one place in which a CLI turn ran, and the first-in-first-out lock in front of it.
- **fail-stop, latch**: the stop of the earlier bridge after an account signal, and its file `fail-stop.json`. The nearest acp2api concept is the lockout.
- **unexpected sign-out**: the old signal name for a sign-in error. acp2api has the state "sign-in required".
- **quota stop, backstop**: the stop of one model group at a threshold of quota use (75% by default), or at a fixed 90% when the quota stop was off. acp2api has the quota wait.
- **model group**: `Gemini Models` or `Claude and GPT models`, the two groups of the `/usage` output.
- **pause**: a state that the maintainer set on the status page. Requests then got `bridge_paused`. acp2api has no such state.
- **engine unavailable**: the old state during the start and after a failed acceptance test (`bridge_engine_unavailable`). The nearest acp2api concept is the state "runtime unavailable".
- **engine error**: the old error code `bridge_engine_error`, for each error of the engine and for each internal error of the bridge. acp2api separates an upstream error from an error that acp2api finds itself.
- **acceptance test**: in the earlier bridge, an automatic check of each new CLI version, before the first CLI turn on that version. The nearest acp2api concept is the compatibility check. In acp2api, "acceptance test" is the check of the project before a release.
- **tested version, tested list**: a CLI version that passed the acceptance test, and the file `tested-versions.json`. The nearest acp2api concept is the accepted version.
- **pending tool call, held call**: a client tool call whose `tools/call` the earlier bridge held open until the tool result came. acp2api uses cancel at permission instead.
- **catalog update**: a text with the full new set of client tools at the start of the next input.
- **step check**: the check of each CLI event against the permitted step types. In the ACP plan, the check of each tool event.
- **agent file, setup text**: the CLI file, and later the ACP text, that carried the system prompt and the tool rules.
- **system text**: the old word for the system prompt.
- **thought content**: the old word for thought text.
- **hosted tool**: the old word for a server tool of the OpenAI Responses API.
- **rebuild header, fixed neutral header**: the old words for the neutral line.
- **rebuild transcript**: the text of the first prompt of a rebuild.
- **heartbeat**: the old word for a keep-alive event.
- **local key**: the old word for the local API key.
- **status page, status JSON**: the page `GET /` and the route `GET /status.json` of the earlier bridge. The nearest acp2api concept is the management panel.
- **bridge MCP server**: the MCP server of the earlier bridge at `/mcp/<token>`. The "token" was a random secret in the path, not the local API key.
- **fake engine**: the test program `test/fake-agy/fake-agy.mjs`, which acted as the CLI.
- **generation identity, error replay**: the key of a request, and the 60-second return of a stored error for a request with the same key.
- **red line**: a rule of the earlier bridge that no code and no test may break.
- **ticket**: a work item T01 to T23 of `mvp-tickets.md`.

## 1. How to use this note

- Each idea has an ID, a behavior "Given ..., when ..., then ...", the acp2api decision that it tests, and its source.
- A source is an old test file with the test name in quotation marks, or a section of an old note. A test name is quoted data, so it keeps the old words.
- "Old:" marks an idea where the earlier bridge expected something else. The line after it gives the acp2api expectation. Do not copy the old expectation into a test of acp2api.
- "(Rewritten for ACP.)" marks a case of the CLI engine whose risk also exists with the official runtime. The text gives the ACP form.
- [#25](https://github.com/yandhi-0421/acp2api/issues/25) is open. It decides the HTTP status, the error body, the stream event, and the retry headers of each error. Thus an idea here says only "an error" or "a refusal".
- Section 2.17 holds the ideas that no acp2api decision covers yet. The PRD must decide each one before a test uses it.
- The links to ADRs and to other notes assume that this note is in `docs/research/`.

## 2. Test ideas by area

### 2.1 OpenAI Chat Completions API: text, streams, and errors

- **CH-1.** Given a model name and one user message with `stream: true`, when the official runtime sends the text chunks `Hel` and `lo`, then the stream has `chat.completion.chunk` events with one `chatcmpl-` ID and an integer `created`. The first chunk has the role `assistant`, the two text deltas come in order, the last chunk has `finish_reason: "stop"` and an empty delta, and the body ends with `data: [DONE]`.
  Decision: [#5](https://github.com/yandhi-0421/acp2api/issues/5). Source: `test/bridge/chat.test.ts`, "streams chatcmpl- chunks with the text Hello from two deltas, finish stop, and [DONE]"; ticket T04.
- **CH-2.** Given `stream: false`, when the prompt turn ends with `end_turn`, then the body is one `chat.completion` with a `chatcmpl-` ID, an integer `created`, and one choice with `index: 0`, `finish_reason: "stop"`, and a message with the role `assistant` and the full text.
  Decision: [#5](https://github.com/yandhi-0421/acp2api/issues/5). Source: `test/bridge/chat.test.ts`, "gives a chat.completion body for a non-stream request, with the same text and usage".
- **CH-3.** Given a streamed request, when the official runtime sends no update for longer than the keep-alive interval, then the stream gets keep-alive events, and the full answer still comes after them.
  Decision: [#14](https://github.com/yandhi-0421/acp2api/issues/14), decision 4, and [#24](https://github.com/yandhi-0421/acp2api/issues/24), decision 3. The written design decides the event of this API and the interval. The earlier bridge chose a `: ping` comment line after 10 s with no event. Source: `test/bridge/chat.test.ts`, "sends a : ping comment line when the engine is silent longer than heartbeatMs".
- **CH-4.** Given a streamed request, when an upstream error ends the prompt turn, then the stream ends with the error form of the API for a stream, and no `finish_reason: "stop"` chunk and no `data: [DONE]` follow it.
  Decision: [#25](https://github.com/yandhi-0421/acp2api/issues/25) (open), and [ADR-0003](../adr/0003-continue-an-acp-session-only-when-a-request-continues-its-history.md) (no continue after an error). The earlier bridge chose a `data:` object with an `error` key. Source: `test/bridge/chat.test.ts`, "ends a stream with a data: error object of bridge_engine_error"; `mvp-spec.md`, "Endpoints".
- **CH-5.** Given `stream: false`, when the official runtime sends some text and then an upstream error ends the prompt turn, then the response is an error, and the ACP session never continues.
  Decision: [#25](https://github.com/yandhi-0421/acp2api/issues/25) (open: it decides the text that came before the error), [ADR-0003](../adr/0003-continue-an-acp-session-only-when-a-request-continues-its-history.md). The earlier bridge gave HTTP 502 with no part of the text in the body. Source: `test/bridge/chat.test.ts`, "gives 502 with an OpenAI error body for a non-stream request" and "gives the first engine error of a turn that wrote text, then failed, then went on; the text is not in the body".
- **CH-6.** (Rewritten for ACP.) Given a prompt turn that ended, when more updates of that prompt turn arrive, then the response does not change. An example is the text chunk `The request was cancelled by the client.` that the official runtime sends after `session/cancel`. That text goes into no response and into no output token estimate.
  Decision: [ADR-0002](../adr/0002-cancel-each-client-tool-call-at-its-permission-request.md) (each cancel adds that text to the history of the ACP session), [#20](https://github.com/yandhi-0421/acp2api/issues/20). Source: `test/bridge/chat.test.ts`, "keeps the answer, the usage, and the Cascade record of the first result when a second result follows"; `acp-engine-plan.md`, section 3, fact 6, and section 6.1 (the rule for `agent_message_chunk` after `session/cancel`).

### 2.2 Anthropic Messages API: text, streams, and errors

- **AM-1.** Given one user message with `stream: true`, when the official runtime sends the text chunks `Hel` and `lo`, then the events are exactly `message_start`, `content_block_start`, `content_block_delta`, `content_block_delta`, `content_block_stop`, `message_delta`, `message_stop`.
  - `message_start` has a message with a `msg_` ID, the type `message`, the role `assistant`, empty content, `stop_reason: null`, and `stop_sequence: null`.
  - `content_block_start` has the index 0 and `{"type": "text", "text": ""}`. Each delta is a `text_delta` at the index 0. `content_block_stop` is `{"type": "content_block_stop", "index": 0}`.
  - `message_delta` has `stop_reason: "end_turn"` and `stop_sequence: null`. The last event is `{"type": "message_stop"}`.

  Decision: [#5](https://github.com/yandhi-0421/acp2api/issues/5) (Claude Code needs the full SSE event order). Source: `test/bridge/messages.test.ts`, "streams the exact event order of section 3.1 with msg_ IDs and the text as text_delta"; [the endpoint contract note](2026-10-05-api-endpoint-contract.md), section 3.1.
  Old: `message_start` had `usage.input_tokens: 0`. acp2api: `message_start` carries a local estimate of the input tokens, see [Which token usage does acp2api report to each API?](https://github.com/yandhi-0421/acp2api/issues/20)
- **AM-2.** Given a streamed request, when the official runtime sends no update for longer than the keep-alive interval, then the stream gets `event: ping`, and the stream still ends with `message_stop`.
  Decision: [#14](https://github.com/yandhi-0421/acp2api/issues/14), decision 4. Source: `test/bridge/messages.test.ts`, "sends the heartbeat as an event: ping when the engine is silent longer than heartbeatMs".
- **AM-3.** Given any prompt turn, when acp2api answers on any API, then the stream and the body have no `thinking` block, no `redacted_thinking` block, no `thinking_delta`, and no `signature_delta`.
  Decision: [#24](https://github.com/yandhi-0421/acp2api/issues/24), decision 1. Source: `test/bridge/messages.test.ts`, "has no thinking or redacted_thinking block in the stream" and "gives a Message with one text block and the same usage for a non-stream request".
- **AM-4.** Given `stream: false`, when the prompt turn ends with `end_turn`, then the body is one Message with a `msg_` ID, the role `assistant`, `stop_reason: "end_turn"`, `stop_sequence: null`, and one text block with the full text.
  Decision: [#5](https://github.com/yandhi-0421/acp2api/issues/5). Source: `test/bridge/messages.test.ts`, "gives a Message with one text block and the same usage for a non-stream request".
- **AM-5.** Given a streamed request, when an upstream error ends the prompt turn, then the stream ends with `event: error`, and no `message_delta` and no `message_stop` follow it.
  Decision: [#25](https://github.com/yandhi-0421/acp2api/issues/25) (open). The earlier bridge used the error type `api_error`, and HTTP 502 with the Anthropic error body for a request with no stream. Source: `test/bridge/messages.test.ts`, "ends a stream with event: error of type api_error, and no message_stop" and "gives 502 with the Anthropic error body for a non-stream request".
- **AM-6.** Given a `system` field as a string, or as several text blocks, when acp2api makes the ACP session, then the full system prompt goes into `_meta.antigravity.systemPrompt.append`, and the parts are joined with one blank line.
  Decision: [#23](https://github.com/yandhi-0421/acp2api/issues/23), decisions 3 and 4. Source: `test/bridge/messages.test.ts`, "accepts the system as a string and as text blocks, and both reach the agent file".
  Old: the system prompt went into the agent file of the CLI. acp2api: it goes in `_meta.antigravity.systemPrompt.append` at `session/new` and at each `session/load`, see [How does the system prompt of a request reach the model?](https://github.com/yandhi-0421/acp2api/issues/23)
- **AM-7.** Given a `role: "system"` message in the `messages` of the Anthropic Messages API after the first user message, as Claude Code 2.1.299 sends, when acp2api makes the prompt, then the message stays at its place with the role label `[system]`, and the match counts it as a user message.
  Decision: [#23](https://github.com/yandhi-0421/acp2api/issues/23), decision 2; [ADR-0003](../adr/0003-continue-an-acp-session-only-when-a-request-continues-its-history.md), "Match". Source: no test of the earlier bridge. #23 records that the earlier bridge rejected such a message in its source code.
  Old: a rejection. acp2api: a message of the conversation with a role label, see [How does the system prompt of a request reach the model?](https://github.com/yandhi-0421/acp2api/issues/23)

### 2.3 OpenAI Responses API: text, streams, errors, and refusals

- **RS-1.** Given `stream: true`, when the official runtime sends the text chunks `Hel` and `lo`, then the events are exactly `response.created`, `response.in_progress`, `response.output_item.added`, `response.content_part.added`, `response.output_text.delta` (two times), `response.output_text.done`, `response.content_part.done`, `response.output_item.done`, `response.completed`.
  - Each event has a `sequence_number`, from 0 upward with no gap.
  - `response.created` and `response.in_progress` carry the same Response object, with a `resp_` ID and `status: "in_progress"`.
  - The message item has a `msg_` ID, and its part is `{"type": "output_text", "text": "", "annotations": []}` at the start. `response.output_text.done` carries the full text.
  - `response.completed` has the same `resp_` ID, `status: "completed"`, and the completed item in `output`.

  Decision: [#5](https://github.com/yandhi-0421/acp2api/issues/5) (Codex needs `response.completed`). Source: `test/bridge/responses.test.ts`, "streams the exact event order of section 3.3 with sequence_number from 0"; [the endpoint contract note](2026-10-05-api-endpoint-contract.md), section 3.3.
- **RS-2.** Given a streamed request, when the official runtime sends no update for longer than the keep-alive interval, then the stream repeats `response.in_progress`. Each repeat has the next `sequence_number` of the stream and the same Response object as the first `response.in_progress`.
  Decision: [#14](https://github.com/yandhi-0421/acp2api/issues/14), decision 4. Source: `test/bridge/responses.test.ts`, "repeats response.in_progress as the heartbeat when the engine is silent" and "gives each heartbeat the next sequence_number of the stream, not a fixed 1".
- **RS-3.** Given `stream: false`, when the prompt turn ends with `end_turn`, then the body is one Response with a `resp_` ID, `status: "completed"`, a numeric `created_at`, and one completed message item with the full text.
  Decision: [#5](https://github.com/yandhi-0421/acp2api/issues/5). Source: `test/bridge/responses.test.ts`, "gives one Response object with status completed, the output message, and the usage".
- **RS-4.** Given `store: true`, when the request runs, then it gets a normal answer, and acp2api stores no response.
  Decision: [#21](https://github.com/yandhi-0421/acp2api/issues/21) (`store` as `false`: ignore). Source: `test/bridge/responses.test.ts`, "accepts store: true, treats it as false, and records nothing".
- **RS-5.** Given `previous_response_id`, an `item_reference` input item, `conversation`, `background: true`, or an `include` value with logprobs, when the request arrives, then acp2api rejects it, the error names the field, and no prompt turn starts.
  Decision: [#21](https://github.com/yandhi-0421/acp2api/issues/21), [ADR-0003](../adr/0003-continue-an-acp-session-only-when-a-request-continues-its-history.md) (the records hold no text). The earlier bridge also told the fix `store: false` for `previous_response_id`. Source: `test/bridge/responses.test.ts`, "refuses previous_response_id with 400 and a message that tells the store: false fix" and the table test "refuses ${refusal.name} with 400 bridge_unsupported and names the field".
- **RS-6.** Given a tool with the type `web_search`, `file_search`, `code_interpreter`, `image_generation`, `computer_use_preview`, `mcp`, `local_shell`, or `tool_search`, when the request arrives, then acp2api rejects it, and the error names the tool. For `web_search`, the error gives the fix `web_search = "disabled"`.
  Decision: [#21](https://github.com/yandhi-0421/acp2api/issues/21) (server tools); [#28](https://github.com/yandhi-0421/acp2api/issues/28), decision 4 (a tool with a `type` that the API client executes, for example `local_shell`, gets the wording `capability_rejected: tool type <type> (name <name>) is not supported by acp2api.`); [#9](https://github.com/yandhi-0421/acp2api/issues/9), decision 4 (`tool_search`). Source: `test/bridge/responses.test.ts`, "refuses a web_search tool with 400 and the Codex fix web_search = \"disabled\"" and the same table test as RS-5.
- **RS-7.** Given `include: ["reasoning.encrypted_content"]`, or a `reasoning` item in `input`, when the request runs, then it gets a normal answer, and no text of the `reasoning` item reaches the official runtime. When the `reasoning` item leaves one user message, the prompt is the text of that message only.
  Decision: [#24](https://github.com/yandhi-0421/acp2api/issues/24), decisions 1 and 2. Source: `test/bridge/responses.test.ts`, "accepts include with reasoning.encrypted_content (no effect)" and "never sends a reasoning item of the input to the engine".
- **RS-8.** Given an `input` that is a string, when the request runs, then the prompt is that string.
  Decision: [#23](https://github.com/yandhi-0421/acp2api/issues/23), decision 8. Source: `test/bridge/responses.test.ts`, "sends a plain string input as the user text of the engine input".
- **RS-9.** Given `message` items with `input_text` and `output_text` parts, and `function_call` and `function_call_output` items, when acp2api does a rebuild, then the text has the user items, the assistant items, the tool call, and the tool result in their order.
  Decision: [#11](https://github.com/yandhi-0421/acp2api/issues/11), [#23](https://github.com/yandhi-0421/acp2api/issues/23). Source: `test/bridge/responses.test.ts`, "parses message items with input_text and output_text parts into user and assistant items" and "parses function_call and function_call_output items into the conversation items". The text form is in MR-10.
- **RS-10.** Given `instructions` and `system` or `developer` input messages before the first message with another role, when acp2api makes the ACP session, then all of them are the system prompt. A `system` or `developer` message after that point stays at its place with its role label.
  Decision: [#23](https://github.com/yandhi-0421/acp2api/issues/23), decisions 1 and 2. Source: `test/bridge/responses.test.ts`, "joins instructions and system or developer input messages into the agent file" and "puts an untyped system or developer item into the system text of the agent file".
  Old: each `system` and `developer` message, at each place, went into the system prompt. acp2api: only the messages at the start, see [How does the system prompt of a request reach the model?](https://github.com/yandhi-0421/acp2api/issues/23)
- **RS-11.** Given an input item with a `role` and no `type`, for example `{"role": "user", "content": "hi"}`, when the request runs, then acp2api uses it as a message item. An item with neither `type` nor `role` gets a rejection that names the type.
  Decision: [#21](https://github.com/yandhi-0421/acp2api/issues/21). Source: `test/bridge/responses.test.ts`, "accepts {\"role\":\"user\",\"content\":\"hi\"} and sends the text to the engine" and "still refuses an item with neither type nor role"; live acceptance note 2, finding F11.
- **RS-12.** Given a conversation of message items with no `type`, where the assistant content is a string or a list of `output_text` parts, when the next request adds one user message, then acp2api continues the ACP session. The same applies when the first request used typed items and the next request uses items with no `type`.
  Decision: [ADR-0003](../adr/0003-continue-an-acp-session-only-when-a-request-continues-its-history.md). The written design decides the normalization of each item before the hash (ADR-0003; [#10](https://github.com/yandhi-0421/acp2api/issues/10), deferred points). Source: `test/bridge/responses.test.ts`, the three tests "continues the Cascade for a history of untyped items (the assistant content is a string)", "... (the assistant content is an output_text part list)", and "continues the Cascade of a request with typed items when the next request uses untyped items".
- **RS-13.** Given a streamed request, when an upstream error ends the prompt turn, then the stream ends with `response.failed`, with `status: "failed"`, an error code, and a message, and no `response.completed` follows it.
  Decision: [#25](https://github.com/yandhi-0421/acp2api/issues/25) (open). Source: `test/bridge/responses.test.ts`, "ends a stream with response.failed that carries error.code and message" and "gives 502 with the OpenAI error body for a non-stream request".

### 2.4 Token usage

- **US-1.** Given a prompt turn with several `usage_update` notifications, when the response ends, then the input tokens are the `used` value of the last `usage_update`: `input_tokens` on the Anthropic Messages API and the Responses API, and `prompt_tokens` on the Chat Completions API.

### 2.13 Lockout, sign-in required, and quota wait

## 4. Test levers of the earlier bridge

### 4.1 Seams

The earlier bridge chose three seams for its tests (`mvp-spec.md`, "Testing Decisions"):

- **The engine command.** The setting `agyCommand` was a list of strings. In tests it ran the fake engine with Node. All other code was real. Tests sent real HTTP requests to a bridge on port 0 and read the SSE stream.
- **The paths.** Tests set the data folder, the workspace, and the CLI projects folder to temporary folders. Each test bridge had one temporary root that held all of them and the scenario of the fake (`test/helpers/bridge.ts`).
- **The timings.** Tests set short values for the keep-alive interval, the idle close, the wait for a tool call, the times of the quota refresh, and the error replay.

A guard made the rule "never run a real engine in tests" automatic. `createBridge` threw when `process.env.VITEST` was set and the engine command did not contain `test/fake-agy/`. The ACP plan put a second guard at the spawn, and it treated `/` and `\` as the same separator (`acp-engine-plan.md`, sections 6.13 and 10, slice S2).

A good test checked a behavior that an API client or the maintainer can see: the HTTP status, the SSE events, the body, the files that the bridge wrote, and the record of the fake. The spec listed each permitted unit test with one reason, for example the pure tables, the gate, the error map, and the state file readers.

### 4.2 The fake engine

`test/fake-agy/fake-agy.mjs` was one Node script with no dependencies. It acted as the CLI from the outside: the same commands, the same stdout NDJSON shapes, the same stderr lines, and the same exit codes.

- **Scenario.** The variable `FAKE_AGY_SCENARIO` gave the path of a JSON file. The scenario had a list of processes. Each new engine process took the next entry, and a state file next to the scenario kept the counter and the state of each conversation (step index, number of turns, sums of the usage, start time). Thus a second process of the same conversation continued where the first one stopped.
- **Defaults.** The version `1.2.17`, the 14 models, and the four `/usage` rows of the live probe of 2026-10-04, all at 100%. The weekly reset times were far in the future, and the five-hour reset times were in the past. The `init` event listed the 60 tool names of a capture.
- **Turn actions.** `text` (text deltas), `plannerDone` (a finished model request with its usage), `step` (any step), `mcpCall` (a call of a tool on the bridge MCP server, with the handshake once for each engine process), `stderr`, `stderrLater` and `rawLater` (a line after a delay, without a wait), `raw` (a stdout line as it is, also a line that is not JSON), `sleepMs`, `result` (with an override of the status, the response, the error, and `denied_actions`), and `exit` (an exit with a code and no result).
- **Captured values.** `capture` was a regex over the input text of a CLI turn. Its first group replaced `{{capture}}` in the text and in the `mcpCall` of the CLI turn, so a scenario could repeat a random value from the prompt of the bridge. A regex with no match ended the engine process with code 2.
- **Fault injection.** A slow `models` (`modelsSleepMs`), a hung `/usage` (`usageSleepMs`), a failed `/usage` (`usageExitCode` and `usageStderr`), an engine process that closed its stdin after its first CLI turn and stayed alive (`closeStdinAfterTurn`), an engine process that was slow to stop and counted each further signal (`sigintExitDelayMs`), and malformed events through `raw`.
- **Record.** The fake appended one JSON line for each event to `record.jsonl` next to the scenario: `argv`, `cwd`, `env`, `init`, `input`, `stdin`, `sigint`, `exit`, and `mcp` (each MCP request, each answer, and each tool step). Each line had the PID and the time in ms. `env` held only the names of the variables, never a value, and only when the scenario set `recordEnv`.
- **Own tests.** `test/fake-agy/fake-agy.test.ts` and `test/fake-agy/mcp-call.test.ts` checked each command, each action, the record, SIGINT, the resume in a new process, and the MCP handshake. Three tests compared the output of the fake with the capture files event for event, and one test compared the key sets of each event type with the captures.
- **Fixtures.** The default event shapes came from the captures. The tests read the capture files and never changed them.

The files in `test/helpers/` gave these levers:

- `startTestBridge` and `disposeAllTestBridges`: a bridge on port 0 with its temporary root, and a cleanup after each test.
- `seedTestedVersion`: it wrote the tested list through the paths seam, so that most tests did not run the acceptance test. A test that needed an untested start wrote `[]`.
- `request`: one raw HTTP request through `node:http`, so a test could set any header, also a wrong `Host`.
- `createSseParser` and `parseSse`: an SSE reader with its own tests. It joined several `data:` lines, kept the `event` field, hid comment lines, read CRLF, and joined events across chunk boundaries.
- `HOLD_UNTIL_SIGINT`: a last action of 30 s for a CLI turn that the bridge must stop. A short sleep had a race: a CLI turn that ended by itself let the fake exit on the end of stdin, before the SIGINT.
- `waitForFakeProcessesToEnd`: a wait before the removal of the temporary root. A fake that still wrote its last records made the removal fail with `ENOTEMPTY`.
- `clean-env.ts`: it removed the red-line variables from the environment of the test process before each test file.
- `catalog-text.ts`: the expected tool texts as literals, as a source of truth that is independent of the code.

### 4.3 Test patterns

- **Literal expectations.** Expected values were literals in the test, for example the usage numbers and the neutral line. The tests did not compute them with the code under test.
- **Markers.** A unique marker string in the message text, the system prompt, the tool arguments, and the tool result. The test then checked that no log, terminal line, state file, or status JSON contained a marker, and that the key did not appear either.
- **Order without races.** A scenario `sleepMs` held a CLI turn open. While it slept, the record could not hold the next input, so the check was an invariant, not a race.
- **Bounded waits.** Each wait for a record line had a limit below the test timeout (for example 5 s of 20 s), so a stall failed with the name of the wait.
- **No real timers where they matter.** The error replay cache used fake timers to check the expiry, the limit of 1024, and the cleanup at the close.

### 4.4 What a fake official runtime for acp2api needs

In ACP words, it is a fake Agent. The plan of the earlier bridge called it the fake ACP server. These needs come from `acp-engine-plan.md`, sections 3, 6.1, 6.5, 6.6, and 6.13, and from the acp2api decisions.

- JSON-RPC 2.0 with one JSON object on each line of stdin and stdout, with the shapes of the captures in [captures/2026-10-15-acp-probe/](captures/2026-10-15-acp-probe/). acp2api also keeps the captures `2026-10-17-macos-probe`, `2026-10-17-macos-token-pdf-slash-probe`, `2026-10-18-windows-probe`, and `2026-10-17-claude-code-check` in `docs/research/captures/`.
- A scenario file with one entry for each runtime process. An entry gives the `initialize` data (`agentInfo` with its version, the auth methods, and the sign-in state) and the prompt turns.
- `session/new` results with the config options `model` and `thinking_level`, `modes.currentModeId`, and `models.availableModels` (section 3, fact 11), so that MN-2 and MN-5 can run.
- A record of each run: the arguments, the `cwd`, the names of the environment variables, each JSON-RPC message in both directions, and each MCP request. For RH-1, the value of `GEMINI_HOME` must also be visible. It is a path, not a secret.
- Turn actions in the vocabulary of the fake engine where possible: text chunks (`agent_message_chunk`), `agent_thought_chunk` (TT-1), a `usage_update`, a client tool call (a `tool_call` with the status `pending` and the title `Run <name>?`, then a permission request with the options `allow_always`, `allow_once`, and `reject_once`), a built-in tool event (the title `Running <tool>` and the status `in_progress`), a permission request of a built-in tool (the command line as the title, or `list_resources`), a stderr line, a sleep, a JSON-RPC error, a stop reason, and an exit.
- After `reject_once`: a `tool_call_update` with `status: failed` and `rawOutput: "Rejected by user"`, and the prompt turn continues (section 3, fact 5).
- On `session/cancel`: the same `failed` update, the text chunk `The request was cancelled by the client.`, and the result `stopReason: cancelled` (section 3, fact 6). A scenario must also be able to ignore a cancel, for RP-5.
- The upstream error line at level `I`: `harness stderr: received model response error: Error <code>, Message: <text>, Status: <STATUS>, Details: [...]`, while the prompt still ends with `end_turn` and the reply text is only the message (section 3, fact 3). The line of the Python server names the ACP session ID (LO-10).
- `session/load` replays the stored history of the ACP session before its result.
- A prompt whose first text starts with `/usage`, after zero or more white space characters, gives the Markdown of the scenario, as the official runtime does ([#23](https://github.com/yandhi-0421/acp2api/issues/23), decision 9). ## 5. Live acceptance checks

### 5.1 Safety rules

These rules of the earlier live acceptance apply to the official runtime (ticket T22; live acceptance notes 1 and 2; `acp-engine-plan.md`, sections 5 and 11):

- The maintainer authorizes the set of checks and the number of requests before the start. The agent gives the number first. The ACP plan approved about 15 prompts for its probe.
- The agent writes each request to a file before it sends it. A request outside the plan uses the request budget of its check. In the live check of 2026-10-06, the agent sent two requests by mistake.
- Count the model requests, not the prompts. In the live check of 2026-10-08, the echo check of the acceptance test sent two model requests, so three checks sent four model requests.
- One Google account. In the earlier live checks, each request started after the previous request ended. acp2api needs a check of three prompt turns at the same time ([ADR-0004](../adr/0004-run-all-acp-sessions-in-one-runtime-process.md)), so the maintainer must authorize that check on its own.
- No 403 on purpose, no sign-in change, no disabled telemetry, and no bypass of a permission. Stop at once after a lockout signal.
- Read no credential file, no keychain entry, and no `state.vscdb`.
- Use a temporary data folder. A wrapper around the real executable keeps a copy of the arguments, the input, the output, and the error output, sends each signal on, and changes no byte.
- Before and after the live check, compare the SHA-256 of the global configuration files, read `/usage`, and count the session files. After the last shutdown, no process of the official runtime may stay.
- Test a stop state with a synthetic state file, not with a real signal. The first live check wrote a synthetic latch file and a synthetic quota file.
- The map of acp2api adds: before a check in the Windows VM, tell the user, because the user must first connect an external drive.
